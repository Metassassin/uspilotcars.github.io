# US Pilot Cars — Modernized Website

A ground-up rebuild of uspilotcars.com: same audience, same sidebar-and-directory mental model, same advertising business — dramatically better presentation, a maintainable data-driven architecture, and a static site that deploys straight to GitHub Pages.

This document is the entry point for the four deliverables the project asked for. The others live alongside it:

- **`SITE_MAP.md`** — old structure vs. new structure
- **`MIGRATION_MAP.md`** — old URL → new URL → redirect status (auto-generated, 173 entries)
- **`ADVERTISING_MODEL.md`** — how ads are represented and how to add one

## What this is, in one paragraph

A 174-page static site (home, directory hub + 61 state/province directory pages, regulations hub + 61 state/province regulation pages, four resource pages, an advertising page, a privacy page, a 404, and 173 legacy-URL redirect stubs), generated by a single dependency-free Python script (`build.py`) from five small JSON data files. No React, no Astro, no npm install, no build service — clone it, run one command, push it, and GitHub Pages serves it.

## Why this architecture

The brief's own priority order (preserve usability → preserve advertising → preserve the sidebar → preserve content → preserve SEO → *then* modernize) points at a data-driven static generator rather than either (a) hand-written HTML per state, which doesn't scale past a handful of states and rots immediately, or (b) a JS framework with a build pipeline, which is more moving parts than a directory site needs and makes "add an advertiser" a developer task instead of a data-entry task. Plain generated HTML also means every page works with JavaScript off, loads fast on the mediocre highway-rest-stop wifi this audience actually uses, and needs zero client-side data fetching for SEO-critical content.

## Design decisions, and why

- **The sidebar is the primary nav, full stop.** It's persistent on desktop, becomes a slide-in drawer on mobile behind a labeled "☰ Menu" button (never hidden entirely), and includes a two-letter placard grid for every US state so "jump to my state" is always one click away, mirroring the muscle memory existing users already have.
- **Ads are structured data, not markup.** Every legacy ad — banner, super listing, bold listing, basic listing — became one JSON object with a `tier`, a `placement` list, and real fields (phone, services, website). This is the single biggest maintainability win: adding an advertiser is a JSON edit and a rebuild, not an HTML edit.
- **Visual direction**: deep navy/charcoal (`#0b1c2b` / `#0f2436`) for the shell and sidebar, warm amber (`#e8871e`) as the one accent color (used for the active nav state, ad banners' top border, and every primary button), white content panels, and a condensed industrial display face (Oswald) paired with a plain, highly legible body face (Source Sans 3) and a monospace "manifest" face (IBM Plex Mono) for phone numbers, state placards, and data tables — a deliberate nod to permit paperwork and highway signage rather than a generic SaaS look.
- **Real content where it exists, honest placeholders where it doesn't.** New Mexico is the fully-migrated flagship state (directory listings *and* regulations, transcribed from the live site during the audit); Texas has a real, migrated hotel list. Every other state renders a clearly-labeled "migration placeholder" panel instead of invented company names, phone numbers, or regulations — per the brief's explicit instruction not to fabricate this kind of information.
- **SEO**: every legacy URL gets a real redirect stub (see below), page titles and meta descriptions are preserved or improved per page, and a `sitemap.xml` + `robots.txt` are generated automatically.

## Legacy URL redirects

GitHub Pages has no server-side redirect config, so `build.py` writes a tiny static HTML file at *every* one of the legacy site's 173 known URLs (`new_mexico_pilot_car.html`, `alabama_truck_stops.html`, `page212.html`, etc.), each containing `<meta http-equiv="refresh">` to the new URL and a `rel="canonical"` pointing at it. That preserves inbound links and as much search-engine equity as a static host allows. The full table is in `MIGRATION_MAP.md`, generated from the same data so it can't drift out of sync with the actual redirect files.

## Adding content later

- **New advertiser** → see `ADVERTISING_MODEL.md`.
- **A state's regulations** → add an entry to `data/regulations.json` under that state's slug (copy the New Mexico entry as a template), then `python3 build.py`.
- **A state's hotel list** → same pattern in `data/hotels.json`.
- **Truck stops** → same pattern in `data/truck_stops.json`.
- **A new state/province** (unlikely, but the framework supports it) → add it to `data/states.json`; every hub page, sidebar placard, and sitemap entry picks it up automatically.

## Running the build locally

Requires nothing but Python 3.8+.

```bash
python3 build.py
```

This regenerates every HTML file in the repository from the templates and data in `build.py` / `data/`. Commit the regenerated files — GitHub Pages serves the committed HTML directly; it does not run `build.py` for you.

## Deploying to GitHub Pages

1. Create a new GitHub repository (or use an existing one) and push this entire folder to its default branch:
   ```bash
   git init
   git add .
   git commit -m "US Pilot Cars — modernized site"
   git branch -M main
   git remote add origin https://github.com/<your-org>/<your-repo>.git
   git push -u origin main
   ```
2. In the repository, go to **Settings → Pages**.
3. Under **Build and deployment → Source**, choose **Deploy from a branch**.
4. Set **Branch** to `main` and the folder to **`/ (root)`**, then **Save**.
5. GitHub will publish the site at `https://<your-org>.github.io/<your-repo>/` within a minute or two (check the **Actions** tab for the "pages build and deployment" run).
6. **If you use a custom domain** (e.g. moving `uspilotcars.com` here): add a `CNAME` file to the repository root containing just the domain name, and point your DNS at GitHub Pages per [GitHub's custom domain docs](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site). Once that's live, update `SITE_URL` at the top of `build.py` to the real domain and re-run the build so canonical URLs and `sitemap.xml` are correct.
7. Every time you edit `data/*.json` and re-run `build.py`, `git add . && git commit && git push` republishes the change — no other deployment step exists.

## Final design test — quick self-check against the brief's four personas

- **Experienced driver**: sidebar, "Pilot Car Directory," and "Pilot Car Regulations" are in the same relative places and worded the same as the legacy nav; the state placard grid replaces scrolling a long link list with one glance.
- **Trucking company employee in a hurry**: home → "Find A Pilot Car" → state tile → phone number is three clicks and the phone numbers are `tel:` links that dial directly on mobile.
- **Advertiser**: New Mexico's directory page shows a real banner ad, a real super listing, and a real bold listing side-by-side so an advertiser can see exactly what tier they're paying for before they buy.
- **Mobile user**: the same three clicks work behind the "☰ Menu" drawer; nothing that exists on desktop is hidden or removed on a phone, per the brief's explicit requirement.

## Known limitations of this prototype

- Ad creative images are SVG placeholders, not real advertiser art (per the brief's instruction not to fabricate business assets).
- Only New Mexico has full regulation and directory content; every other state/province is a clearly-labeled placeholder, ready for real migration.
- Truck stop listings are a framework with no per-state data yet — the legacy per-state truck stop pages weren't captured during this audit round.
- `SITE_URL` in `build.py` is a placeholder domain; update it once you know the real GitHub Pages URL or custom domain, then rebuild.
